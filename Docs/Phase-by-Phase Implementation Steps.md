# AGCP Deterministic Query Understanding — Phase-by-Phase Implementation Steps

This document is the step-by-step execution guide for replacing the current
rule-based `QueryAnalyzer` with a deterministic query-to-repository retrieval
pipeline. Each phase is self-contained, testable, and builds on the previous one.

Reference plan: `Docs/Deterministic Query Understanding - Implementation Plan.md`.

---

## Confirmed Design Decisions

- `analyzeQuery()` remains a **thin wrapper** returning the legacy
  `QueryAnalysisResult`. The new engine adds `planContext()` returning `ContextPlan`.
- Metadata (keywords/phrases/error signatures) is generated by a **separate
  source-scan pass** (`RepositoryIndex`). `TreeSitterExtractor` and its tests stay
  untouched.
- Graph tests live in `src/graph/` and run via a **new npm script** (`test:graph`).
- BM25 is implemented **in-house** with zero new dependencies.
- Target module: `src/graph/` (flat, matching existing convention), types extended
  in `src/graph/types.ts`.

---

## Phase 0 — Contracts & Benchmark Harness

**Goal:** Freeze interfaces and create the scoring baseline before writing logic.

### Steps
1. Extend `src/graph/types.ts` with:
   - `RetrievalStatus = 'matched' | 'ambiguous' | 'insufficient_evidence'`
   - `QueryAction = 'fix' | 'create' | 'modify' | 'refactor' | 'explain' | 'unknown'`
   - `QueryFeatures` (`action`, `symptoms`, `entities`, `constraints`,
     `identifiers`, `errors`, `raw`, `normalized`)
   - `RepositoryIndexEntry` (id, name, filePath, type, startLine, endLine,
     identifiers, keywords, phrases, errorSignatures, imports, exports, parentId, role)
   - `RetrievalEvidence` (`exactMatch`, `errorMatch`, `lexicalRelevance`,
     `roleRelevance`, `graphRelevance`)
   - `RankedCandidate` (filePath, score, matchedTerms, matchedSymbols,
     matchedErrors, graphReasons)
   - `ContextPlan` (`query`, `operation{action,confidence}`, `candidates[]`,
     `dependencies[]`, `status`, `truncated`)
2. Create `data/benchmark.json` containing the query test matrix, each entry with
   `query` and `expectedFiles` (globs).
3. Create `src/graph/evalRetrieval.ts`: loads a produced `ContextPlan` per query
   and computes Recall@5, Precision@5, MRR, latency, and token reduction.
4. Add scripts to `package.json`: `eval` -> `tsx src/graph/evalRetrieval.ts`.
5. Add script `test:graph` -> `tsx --test src/graph/*.test.ts`.

### Deliverables
- Updated `src/graph/types.ts`
- `data/benchmark.json`
- `src/graph/evalRetrieval.ts`
- `package.json` scripts (`eval`, `test:graph`)

### Exit Criteria
- `npm run build` passes.
- `npm run eval` loads the benchmark without error.

## Phase 1 — Query Preprocessor & Vocabulary

**Goal:** Deterministic normalization and terminology, with no repository dependency.

### Steps
1. Create `src/graph/QueryPreprocessor.ts`:
   - Preserve the original raw query.
   - Produce a normalized form (lowercased, whitespace-collapsed, punctuation-stripped).
   - Detect filenames, extensions, line numbers, identifiers, and error codes
     via targeted regexes (regex is acceptable here).
   - Separate pasted logs/stack traces/code snippets from the user description.
2. Create `src/graph/QueryVocabulary.ts`:
   - Symptom maps: `crash` -> runtime failure; `doesn't respond` -> unresponsive
     interaction; `not showing` -> rendering/visibility; `not reaching server` ->
     request dispatch/network flow; `wrong result` -> incorrect data/business logic.
   - Action synonym maps for `fix/create/modify/refactor/explain`.
   - Data-only exports (no logic), so the maps are configurable.
3. Add `src/graph/QueryPreprocessor.test.ts` and `QueryVocabulary.test.ts`.

### Deliverables
- `src/graph/QueryPreprocessor.ts`
- `src/graph/QueryVocabulary.ts`
- `src/graph/QueryPreprocessor.test.ts`
- `src/graph/QueryVocabulary.test.ts`

### Exit Criteria
- `npm run test:graph` passes for preprocessor and vocabulary tests.
- Preprocessing a stack trace yields separated identifiers and error frames.

## Phase 2 — Query Feature Extractor

**Goal:** Extract independent signals instead of assigning one intent too early.

### Steps
1. Create `src/graph/QueryFeatureExtractor.ts` using `QueryPreprocessor` +
   `QueryVocabulary`:
   - **Action:** `fix/add/explain/replace/refactor`; else `unknown` (never default
     to `modify`).
   - **Symptoms:** normalized via vocabulary.
   - **Entities:** login, API, keyboard, partner, database, etc.
   - **Constraints:** Android-only, specific screen, no API changes.
   - **Explicit identifiers and error messages.**
2. Rework `src/graph/QueryAnalyzer.ts` so `analyzeQuery()` delegates to
   `QueryFeatureExtractor` while still returning legacy `QueryAnalysisResult`
   (map new features back to `intent`, `operations`, `extractedKeywords`,
   `targetSymbols`).
3. Update `src/graph/testQueryAnalyzer.ts` to display the new feature output.
4. Add `src/graph/QueryFeatureExtractor.test.ts` covering the matrix prompts.

### Deliverables
- `src/graph/QueryFeatureExtractor.ts`
- Updated `src/graph/QueryAnalyzer.ts` (wrapper)
- Updated `src/graph/testQueryAnalyzer.ts`
- `src/graph/QueryFeatureExtractor.test.ts`

### Exit Criteria
- "Why does login fail?" and "Fix login failure" share entities/symptoms and
  differ only in `action`.
- `query: "foo bar"` yields `action: 'unknown'`, not `'modify'`.

## Phase 3 — Behavior-Aware Repository Index

**Goal:** Turn `graph.json` + source into searchable, behavior-aware metadata.

### Steps
1. Create `src/graph/RepositoryIndex.ts`:
   - Normalize/dedup file paths (fix duplicate `FILE` nodes and relative/absolute
     inconsistency from `graph.json` / `output.json` / `day3-symbols.json`).
   - Build `RepositoryIndexEntry[]`:
     - `identifiers` from symbol names, parameters, and referenced names.
     - `keywords` from camelCase/snake_case splitting + path segments.
     - `phrases` from comments/docstrings (light source scan).
     - `errorSignatures` from `throw`/`Error`/exception patterns (light source scan).
     - `imports`/`exports` from existing `IMPORTS` edges and export symbols.
     - `parentId` from `CONTAINS` edges.
     - `role` inferred from path/name/AST (screen, api, endpoint, service, model,
       ui, middleware).
   - Build inverted indexes once: name, path, identifier, error signature, phrase, role.
   - Persist to `data/index.json`.
2. Add `npm run index-graph` -> `tsx src/graph/RepositoryIndex.ts`.
3. Add `src/graph/RepositoryIndex.test.ts` (builds index over this repo, asserts
   dedup and expected role/error metadata).

### Deliverables
- `src/graph/RepositoryIndex.ts`
- `data/index.json` (generated)
- `package.json` script `index-graph`
- `src/graph/RepositoryIndex.test.ts`

### Exit Criteria
- Index builds for this repo with unique file paths.
- Lookups are map-based (no per-keyword full graph scans).

## Phase 4 — Multi-Strategy Retriever

**Goal:** Implement the four retrieval strategies and merge candidates.

### Steps
1. Create `src/graph/LexicalRanker.ts`: in-house BM25 with tokenizer, corpus
   stats, and configurable `k1`/`b`.
2. Create `src/graph/RepositoryRetriever.ts`:
   - **Strategy 1:** exact identifier/path/symbol match (highest priority).
   - **Strategy 2:** error/log signature match against indexed `errorSignatures`.
   - **Strategy 3:** keyword/phrase retrieval via `LexicalRanker` over inverted indexes.
   - **Strategy 4:** graph-seed expansion from graph nodes/relationships.
   - Merge all strategy outputs, attaching per-strategy evidence tags.
3. Add `src/graph/LexicalRanker.test.ts` and `RepositoryRetriever.test.ts`.

### Deliverables
- `src/graph/LexicalRanker.ts`
- `src/graph/RepositoryRetriever.ts`
- Test files for both

### Exit Criteria
- Each candidate carries provenance (which strategy matched and on what terms).
- Exact filename/identifier matches rank above generic keyword matches.

---

## Phase 5 — Evidence Scoring, Ranking & Confidence

**Goal:** Combine signals into a ranked, explainable result set.

### Steps
1. Create `src/graph/ContextRanker.ts`:
   - `scoreCandidate(RetrievalEvidence)` with weights:
     exact `.30`, error `.25`, lexical `.20`, role `.15`, graph `.10`.
   - Normalize signals; avoid double-counting the same evidence.
   - Apply explicit-match priority so a named file isn't outranked by a keyword.
   - Emit `RankedCandidate` with `matchedTerms`, `matchedSymbols`, `matchedErrors`,
     `graphReasons`.
   - Map score -> `RetrievalStatus` via thresholds (matched/ambiguous/insufficient).
2. Add `src/graph/ContextRanker.test.ts` asserting ordering, reasons, and status
   mapping (including the ambiguous case with two similar screens).

### Deliverables
- `src/graph/ContextRanker.ts`
- `src/graph/ContextRanker.test.ts`

### Exit Criteria
- Two similarly-scoring unrelated files yield `ambiguous`.
- Every ranked candidate includes human-readable reasons.

---

## Phase 6 — Adaptive Graph Expansion & Context Planning

**Goal:** Expand top candidates into the minimal supporting code (AGCP core).

### Steps
1. Create `src/graph/ContextPlanner.ts`:
   - Seed from top-ranked candidates.
   - Bounded BFS over `imports`, `calls`, `calledBy`, `references`, `contains`.
   - Add a reverse-edge (`calledBy`) index if not already present.
   - Enforce visited set, relevance thresholds, and a context budget.
   - Dedup files/symbols.
   - Reuse `DependencyBuilder`, `ContextExtractor`, `MinimalContextGenerator` for
     code extraction.
2. Add `src/graph/ContextPlanner.test.ts` covering bounded expansion and budget stop.

### Deliverables
- `src/graph/ContextPlanner.ts`
- `src/graph/ContextPlanner.test.ts`

### Exit Criteria
- "booking not reaching partners" seeds the booking service, then pulls partner
  selection + distance filter + callers within budget.
- Expansion stops at the budget and sets `truncated` when cut off.

---

## Phase 7 — ContextPlan Service & CLI Wiring (MCP-Ready)

**Goal:** Emit structured, traceable output and wire the full pipeline.

### Steps
1. Create `src/graph/MCPContextService.ts` returning `ContextPlan`:
   - `operation{action,confidence}`
   - `candidates[]{filePath,score,reasons,relevantRanges}`
   - `dependencies[]{source,target,relationship}`
   - `status`, `truncated`
2. Create a CLI entry `src/graph/planContext.ts` chaining:
   preprocess -> features -> retrieve -> rank -> plan.
3. Add `npm run plan -- "<query>"` -> `tsx src/graph/planContext.ts`.
4. Keep `analyzeQuery()` as the legacy wrapper for existing scripts/tests.
5. Add `src/graph/MCPContextService.test.ts` validating the output contract.

### Deliverables
- `src/graph/MCPContextService.ts`
- `src/graph/planContext.ts`
- `package.json` script `plan`
- `src/graph/MCPContextService.test.ts`

### Exit Criteria
- `npm run plan -- "I'm getting JWT expired"` prints a `ContextPlan` with
  evidence-backed candidates and an honest `status`.
- The MCP server SDK + tools remain future work; this phase is MCP-ready only.

---

## Phase 8 — Benchmark Evaluation & Tuning

**Goal:** Validate and tune retrieval quality against real prompts.

### Steps
1. Run `npm run eval` across `data/benchmark.json`.
2. Record Recall@5, Precision@5, MRR, latency, and token reduction.
3. Tune scoring weights, thresholds, and context budget.
4. Document metrics and tuning notes in `Docs/`.
5. Optionally add regression thresholds to the eval script.

### Deliverables
- Benchmark results (documented)
- Tuned weights/thresholds
- Updated documentation

### Exit Criteria
- A documented baseline exists for Recall@5 / MRR / latency / token reduction.
- No optimization sacrifices correctness for smaller context.

---

## Cross-Phase Notes

- **Data caveats (Phase 3):** duplicate `FILE` nodes (basename vs full relative
  path), inconsistent relative/absolute paths, and syntax-level-only `MODULE`/
  `reference` nodes must be normalized before indexing.
- **Testing:** new tests run under `npm run test:graph`; existing AST tests stay
  under `npm test` (`tsx --test src/ast/*.test.ts`).
- **Dependencies:** no new npm packages; BM25 and tokenizer are in-house.
- **MCP boundary:** this plan stops at the `ContextPlan` service and CLI. The MCP
  server SDK, tool registration, and patch validation are a separate later effort.
